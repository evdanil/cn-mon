# cn-mon development and review plan

M0's specification/license foundation and M1's executable/target/model foundation are merged in [PR #7](https://github.com/evdanil/gotest/pull/7) and [PR #8](https://github.com/evdanil/gotest/pull/8). M2 native-probe implementation is authorized and in progress. This plan defines the component and integration gates for **cn-mon** in `evdanil/gotest`; no later milestone is complete merely because its contracts are documented.

## Working rules for every milestone

1. Use **Astra at xhigh** for architecture and code review and **Luna at high** for implementation agents, as requested. Verify the assigned model/effort; do not silently substitute or claim a model was used when unavailable. Delegate implementation in bounded packages/behaviors with shared contracts; avoid concurrent edits to the same files. Delegation is permitted by the user's explicit agent request.
2. Practice TDD: select acceptance IDs; write a failing behavior test/fixture first; demonstrate the expected failure; implement the smallest change; run it green; refactor with tests green. Record concise red/green evidence in the PR. Do not merge failing tests or use network silence/public DNS as a deterministic test oracle. Do not write tests that merely restate implementation constants.
3. Apply KISS, DRY and YAGNI: reuse proven permissive libraries, isolate only actual nondeterministic boundaries, and add no unrequested subsystem. Resolve architectural contract changes in the specification before implementations diverge.
4. Refresh README, help/examples, architecture/behavior documentation, dependency notices and this progress checklist after each major milestone as relevant. State implemented, partial and unverified capabilities accurately. Required tests, runtime permissions and known limitations belong with the feature they describe.
5. Deliver each milestone as a separate branch and PR to `evdanil/gotest` targeting `main`. Keep PRs reviewable and dependency ordered; dependent work may prepare locally but cannot bypass the prior gate. Never commit unrelated setup artifacts, credentials or user changes. No direct push to `main`.
6. Run appropriate local checks; request an **Astra xhigh** code review; fix its findings. Publish the PR with acceptance mapping, concise behavior/validation evidence and remaining limitations. Trigger the external Codex reviewer with the exact PR comment **`@codex review`**. This task explicitly authorizes that review request.
7. Monitor CI checks, external review results and comments. Fix actionable findings, refresh docs, rerun affected checks, and request review again after material changes. Dismiss a finding only with a recorded technical explanation and reviewer resolution where required. A posted review request is not completed review; no response/timeout is not approval.
8. Merge into `main` only when the current reviewed commit has all required checks green, Astra review is resolved, external Codex review has completed with no unresolved actionable findings, and repository protections allow merging. Do not equate cross-compilation or skipped native tests with a passed runtime gate. If API/network access or a reviewer is unavailable, preserve the completed branch/PR and report the precise blocked publication/review step; do not bypass it.

Use the existing isolated checkout; do not create a worktree merely for onboarding. The refreshed cloud setup helper activates cn-mon's module environment with `GO111MODULE=on` and `GOTOOLCHAIN=local`; an additional override of the old Hello World module setting is no longer required. The available Go toolchain is `/workspace/.cloud-setup/gotest/toolchains/go1.27.2/bin/go`. Setup scripts remain outside application code unless a later coding milestone deliberately introduces a repository development helper.

## Milestone dependency order

```text
M0 specification/license boundary
 └─ M1 executable foundation + target/model contracts
     └─ M2 native ICMP/TCP and two-platform feasibility gate
         └─ M3 compatible persistent history
             └─ M4 complete run engine + machine output
                 └─ M5 list/show/follow + live terminal + human formats
                     └─ M6 release qualification and delivery
```

M1's component gate is complete; M2 and later gates remain pending. An acceptance ID referenced before its full integration milestone covers only the explicitly named component portion; it is not a claim that the entire scenario is complete. Operational target commands arrive in M4, reader commands and terminal integration in M5, and the full release-binary matrix in M6. Do not implement later commands merely to satisfy an earlier component gate. If a milestone becomes too large for useful review, split it into dependent PRs while keeping its combined acceptance gate and documentation current.

### M1 — executable, targets and pure monitor model (merged)

Create the Go module at `github.com/evdanil/gotest`, `cmd/cn-mon`, the minimal internal package boundaries and pinned toolchain/module configuration. Replace the starter program through the normal coding PR. Pin permissive dependencies and notices, including the SQLite driver/terminal primitives when first needed; do not import unused frameworks. Add native Linux/Windows CI for deterministic tests/builds from the beginning.

First write source-derived input/canonicalization/golden-ID fixtures, narrow INI/configuration/logging fixtures and pure tracker tests. Record provenance for configuration fixtures from the pinned cn-tool `main.py`, `utils/config.py` and `utils/logging.py`, including the native executable-directory mapping for its launcher layer. Implement only the five effective keys and CLI overrides specified in application section 2.1; keep this in small native support code, not a general framework. The approved scope excludes Python hooks/custom-plugin loading and any Python adapter; retain built-in monitor behavior and do not introduce a Python runtime. Cover reference subnet exclusions, scope IDs, port validation, one-round spacing, observed periods, state precedence and concurrent sample-time clamping. Implement only enough command parsing/help/version and startup validation to establish the CLI contract; document remaining runtime modes as pending until integrated.

Acceptance: **CLI-01, CLI-02, CFG-01, CFG-02, TGT-01, TGT-02, MOD-01, MOD-02, MOD-03** at parser/configuration/model contract level. Verify INI discovery/precedence/grammar/coercion/fallback, logging setup and its failure boundary, and no configuration/log/history side effects on the implemented help/version or invalid-CLI paths. Operational command startup/exit behavior is deferred to M4/M5. Characterize the complete retained option/alias map in application section 2 against the pinned `main.py`: all six short/long pairs; mixed `--file first.txt -f second.txt` using only the last file; `-f -` and duplicate positional `-` reading stdin once; all three reader modes rejecting `-f/--file` before stdin/file reads; and both `-h/--help` and `-v/--version` exiting without data I/O. Excluded cache/credential/XLSX flags remain usage errors; do not implement their source frameworks. Include repeated `--config first.cn --config ""` and `--log-file first.log --log-file ""`: the last empty value adds no explicit configuration layer/log override and never revives the earlier value. Inputs cover the exact golden request in the specification, changed ports/trailing dots, equivalent CIDRs, IPv4 dotted netmask/hostmask forms with identical expansion/key to `/24`, invalid masks, overlapping inputs, `/31`/`/127`, and UTF-8/BOM/stdin failures. Include all TCP admission/identity fixtures in specification section 3: reversed inputs at exactly 1,024 hosts retain equal keys when the accepted canonical sets agree; reversed over-cap inputs may admit different sets and produce different keys; case-variant names consume separate pre-canonical admission slots even if identity later merges them. Preserve the source's greedy input-order admission; do not implement a new sorted selection policy. Clock-independent model tests include no-history, zero-seen, changing DNS address supplied as fixture data, and many synthetic rounds without sleeping; slot scheduling belongs to M4.

Gate: formatter, `go vet`, meaningful `go test` on both native OSes, race checks on supported runner configurations, and bounded-memory synthetic target/model checks. README/help show the product name, supported targets, build/test commands, the retained `.cn` layers and five settings with CLI overrides, output expectations and implementation status. Freeze reviewed first-party and dependency licensing inventory, including any small INI parser used.

Implementation boundaries for the independent Luna agents:

- **CLI/scaffold:** own `go.mod`, `cmd/cn-mon/main.go`, `cli*.go` and their tests, native CI and notices. Parse options without data I/O; retain explicit presence for file/schedule/history overrides and resolve `--since` once against an injected command-start time. Help/version exit 0, invalid/no-argument invocations exit 2, and recognized operational modes exit 3 with an explicit not-yet-implemented diagnostic. Those unavailable modes read no target input/configuration and open no logs, history or sockets in M1; component tests establish the future startup contracts independently. Do not simulate a successful monitor run.
- **Targets:** own `internal/target`. `ReadObjects` collects ordered positional/file/stdin input; `ParsePorts` validates the text; `Build` returns the canonical `Request` (`Tokens`, `Ports`, `Hosts`, `Key`), ordered input rejections, and an error for invalid direct-caller parameters. An invalid target is a rejection, not a fatal build error; valid targets survive. Input collection and canonicalization remain separate. Preserve pre-canonical greedy admission and the source request-key byte encoding; perform no DNS or network I/O.
- **Configuration/logging:** own `cmd/cn-mon/config*.go`, `logging*.go` and their tests/fixtures, sharing package `main` without editing the CLI agent's files. `loadSettings` takes explicit executable/home/working-directory context and CLI overrides and returns effective settings plus diagnostics; it never opens a logger. `openLogger` separately prepares/appends the configured log with the source fallback behavior. Preserve Python integer coercion with standard-library arbitrary-precision integers rather than silently narrowing valid retention values to `int64`; retention arithmetic remains M3 work. No credential/configuration framework is introduced.
- **Pure model:** own `internal/monitor`. Typed rows and complete rounds feed observation/failure helpers and an aggregate tracker; pending observations affect display only. Callers precompute fixed inferred spacing and feed rounds in `(started, round_id)` order, rebuilding when spacing or the selected window changes. The tracker retains only aggregate host state, required periods and previous start/interval. Summary queries receive whether the latest round's owner is live; another live run cannot open its periods. Sparse seen rows retain the last responding address, while an unseen latest observation clears TCP fields. The source tracker's `HadError` means an `E` observation; the separate execution-failure helper detects errors masked by a seen character and will feed current-run exit calculation in M4.

Keep M1's module graph free of unused external dependencies; ICMP, SQLite and terminal dependencies enter at M2, M3 and M5 respectively. Do not create placeholder packages for them. Each agent records an actual failing behavior test and its subsequent passing result, with source-fixture provenance; compiler failures alone do not establish a behavioral regression test. The shared API contracts must be agreed before production edits, and the root integrates/test-runs them together before independent review. Linux and Windows native CI results are required for the M1 gate; a cross-build or an unavailable runner is not a pass.

### M2 — native ICMP, TCP and runtime feasibility (in progress)

This milestone retires the principal platform risk before persistence/UI work grows around an unproved backend. Add the pinned scoped pro-bing adaptation and keep an explicit upstream patch/provenance record. Use fixtures to prove the unmodified behavior fails required error-attribution tests, then add the smallest extension: structured error callback, quoted-packet correlation, sufficient receive buffers, admission through Linux filtering, active identifier management, and reply-over-error aggregation. Retain upstream core assertions while replacing public-DNS dependencies with injected/literal fixtures and moving genuine raw-socket cases into the controlled opt-in native suite; run nested-module tests explicitly.

Build the context-cancellable DNS and TCP adapters and the bounded batch executor. Keep one new product package, `internal/probe`, independent of the monitor model. `Resolve` returns ordered resolved/unresolved entries after at most 100 concurrent application lookups; `ProbeBatch` accepts at most 100 resolved entries and returns ordered ICMP/TCP results with execution errors separate from reachability states. Cancellation returns no completed batch. M4 owns round completion and records batch timestamps before calls. Resolve all names before probing; TCP's 3-second deadline starts per admitted attempt, not at the beginning of a potentially multi-wave batch.

Use captured/generated packet fixtures for every type/family and an injected packet connection for races/deadlines/cancellation. Keep two successful-send ledger entries independently of pending replies, so errors still correlate after a first echo while the pinger is active. Test fast receive against send publication and target/intermediate deduplication. Serialize publication/correlation, unlock before callbacks, and interrupt the socket without needing that lock. Both parent cancellation and the 3-second ICMP host deadline must interrupt a `WriteTo` blocked until close/deadline before joining workers; regress both paths and preserve their distinct cancellation/reachability outcomes. Join application-owned workers/sockets and return promptly from DNS cancellation; Go's native Windows `GetAddrInfoW` may finish later and is not claimed to have stopped. Fuzz only hostile parsing boundaries: malformed ICMP/IP quotations and extension chains; seeded deterministic tests still run normally. Use local TCP listeners and injected route/resource errors rather than uncontrolled public services.

Bounded Luna ownership: ICMP adaptation/identifier allocator; resolver/TCP/batch API; native test harness/CI; and root module/notices/README integration. The integration owner alone edits root `go.mod`/`go.sum`. Astra owns application specification/development-plan amendments and shared contracts; an independent Astra reviewer checks them. No concurrent edits to the same file; root coordinates Git/reviews. No SQLite, terminal framework or operational command enters M2.

Acceptance: **DNS-01, PRB-01, PRB-02, PRB-03, PRB-04** at resolver/probe/batch API level. Use native package test harnesses, not an operational target command; round-to-round resolution, combined command outcomes and exit codes are integrated in M4. Real native tests must exercise both IPv4 and IPv6 echo. In isolated test infrastructure, provoke at least one target-sourced rejection and one intermediate-sourced error for each family and verify receive/filter/correlation behavior; packet-decoder tests alone do not prove the OS delivers required packets. Linux namespace reject rules establish real rejection-only aggregation. Windows may use a test-only raw emitter quoting an active request through actual sockets, asserting correlated sender/destination/identity callbacks even when loopback echo also arrives; replies must still win. This establishes OS delivery without requiring an unfinished product command or an echo-suppressed Windows aggregate. Pure fixtures retain all error/reply ordering and rejection-only aggregation assertions. Windows sender-unavailable cases must remain honest no-response cases. Compare a genuine ordinary-user context and elevated Windows behavior, and Linux denied/granted raw-socket access; publish actual results rather than upstream README promises.

Gate: native Windows and Linux jobs, upstream-core adaptation tests, race tests around cancellation/reply/error races, no subprocess probes, 100-host concurrency cap and two-reply accounting. Start with disposable hosted runners: namespace-local Linux topology and bounded Windows raw-emitter/temporary-alias experiments, recording actual tokens, events and cleanup. Temporary network/firewall changes are test infrastructure confined to disposable runners, never product behavior. Required runtime cases are not silently skipped; if a specific required case cannot be established there, use an authorized isolated native runner/lab and attach reproducible evidence. Do not assume such infrastructure is already available. No changes to the user's host firewall, capabilities or sysctls are made automatically. If the backend fails an essential platform behavior, stop the dependent implementation milestone and revise architecture through review; do not weaken the acceptance contract.

Docs: actual runtime permission/install instructions, clear permission-denied behavior, IPv6 availability rules, probe timing and library patch maintenance instructions.

### M3 — schema-1 SQLite history and interoperability

Implement the small `database/sql` store with the pinned CGO-free SQLite driver. Generate representative SQLite schema-1 fixtures from the pinned cn-tool reference in a separate test-fixture preparation step; commit fixtures/provenance so Go's ordinary tests need no Python. Include a controlled interoperability check that cn-tool reads Go-created/appended history correctly. Retain all notices needed for adapted schema/logic.

Write transaction/failure tests before writes: cancel/fail during request creation and mid-round insertion; verify rollback. Then implement safe schema validation, WAL writer setup, parameterized writes, read-only store APIs, paging/snapshots, retention and lifecycle state. Inject read/write/commit/close/lock errors and verify the store error boundary; do not mock away every real SQLite behavior. Use real temporary databases and separate connections/test-helper processes for concurrency and killed-writer recovery. Target-run orchestration, in-memory fallback/exit codes, and list/show/follow commands remain M4/M5 work.

Acceptance: the transaction, schema, retention and read-only store portions of **DB-01, DB-02, DB-03**, plus the query/lifecycle-state portion of **HIS-01**. Compose M1's **CFG-01/CFG-02** configuration resolver contracts with store API calls; no command end-to-end behavior is claimed here. In temporary homes, resolve settings for the fallback `~/.cn-ping-history.db` and an INI-configured path, then verify store APIs read/append each selected database. Resolve INI retention of 90 days, call pruning explicitly, and verify a 45-day-old round survives; resolve an explicit 30-day override, call pruning, and verify it is removed. Similarly pass a resolved `--history-file` override to the store and verify independent file selection. Include filenames with spaces/Unicode/URI punctuation, Windows paths, missing/unreadable files, existing WAL, unknown/newer/corrupt schemas, read-only API non-mutation, out-of-order commits, autoincrement non-reuse, prefix-query results, stale/inaccessible local PIDs, zero-round live runs and intervals exceeding retention. Command startup ordering and logging-failure-before-prune checks belong to M4 for target runs and M5 for readers; complete **HIS-01** command behavior belongs to M5.

Gate: real SQLite component tests on both native OSes, store-level interoperability evidence in both directions, no external SQLite runtime, CGO-free build, clean licensing inventory. Schema compatibility is supported by API-generated/read fixtures and fault/concurrency checks; this gate does not require operational cn-mon commands.

Docs: schema/invariants, retained `[ping]` path/retention settings and fallback `~/.cn-ping-history.db`, `.cn`/`-c` precedence, `--history-file`/`--history-days` overrides, local-filesystem requirement, supported backup procedure (SQLite backup/checkpoint-aware copy), retention, permissions and read-only limitations. Do not tell users to copy only a live database file while its WAL contains data.

### M4 — run orchestration, cancellation and JSON

Connect targets, probes, tracker and store with one state owner. Test scheduling against fake wall/monotonic clocks first. Add slot alignment, overrun handling, duration bounds, heartbeat, historical snapshot inclusion, per-round atomic completion, store failure fallback, signal/control abstraction, outcome/exit-code calculation and final JSON rendering. No UI is required to prove the engine.

Acceptance: **RUN-01, RUN-03**, the engine/target-command portions of **RUN-02/OUT-01**, integrated target-mode **CLI-01/CFG-01/CFG-02/DB-01/DB-02**, and regression of prior component checks. Run end-to-end target commands using default/INI history paths and retention, with and without CLI overrides; verify a 45-day-old round survives configured 90-day retention and is pruned by a 30-day override. Prove actual target-command startup resolves settings before history effects and a logging initialization failure cannot open/prune history. Exercise fresh DNS each round and combined probe success/failure exit codes. Test cancellation during resolving, probing, waiting, read/lock wait and committing; complete-vs-incomplete round boundary; first/second Ctrl+C semantics; forward/backward clocks; all-invalid/partially-valid/all-unresolved targets; a past open TCP port with current silence; no current completed round despite earlier seen data. Ensure errors in cancelled partial rounds do not poison committed outcomes. Terminal restoration/live rendering in **RUN-02/OUT-01** awaits M5.

Use subprocess tests for real signal/process lifetime/exit code and redirected stdout/stderr, plus local TCP/loopback native smoke tests. Run-engine tests must not wait minutes/hours to exercise schedules. Check goroutine/socket cleanup at cancellation and memory growth over many synthetic rounds; retain only aggregate state, required periods, and current rows.

Gate: both OS unit/integration jobs and target-run JSON goldens pass, no stdout progress contamination, a real native one-round command recording is read back through the store API, no partial-round history survives cancellation, and store failure continues in memory and prints available JSON with exit 3. Reader commands are not required for this gate.

Docs: usable target-run examples, scheduling/window/exit-code contract, sampled-period limitation, JSON field semantics and current implementation status.

## Current evidence and unresolved verification

Source behavior was inspected at the pinned cn-tool revision. The pro-bing and Digineo source revisions above were inspected; deterministic pro-bing packet tests showed that non-echo messages are currently ignored. This supports the need for an extension, **not** that the proposed extension works. M1's component implementation, native Linux/Windows checks and internal/external reviews passed its merge gate in [PR #8](https://github.com/evdanil/gotest/pull/8), merge commit `e958cff`. The approved exceptions exclude the interactive menu, XLSX, and Python `process_data` hooks/custom-plugin framework; no Python adapter or runtime is included. No shipped plugin targets the monitor, but custom callbacks can alter/drop rows before history and exit-status calculation, so that custom behavior is explicitly outside compatibility rather than treated as equivalent. Each implementation milestone remains subject to the normal internal/external review and green-check merge gate. Exact dependency versions beyond the reviewed ICMP source are pinned at first use after their platform/license checks; compatibility discoveries require a documented reviewable amendment, not an implicit feature loss.
