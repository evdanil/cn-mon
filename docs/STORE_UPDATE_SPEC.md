# Automatic Microsoft Store updates

Status: implemented on `feat/store-update-ci`; automated tests and Linux-side package/controller harnesses pass. The owner reported successful submission of package `1.3.2.0` on 2026-10-17. This is not evidence that Store certification or publication has completed. The package contains CLI `0.3.0` and uses the reserved display name `cn-mon — Network Monitor`. Store API credentials are not configured; no live Store API call has been made. The actual Windows SDK packaging and qualification job remains a required PR-CI check.

## Outcome and scope

After a stable GitHub release is published in `evdanil/cn-mon`, automatically verify its published payload, construct and qualify an x64 MSIX, and submit a package-only update for certification and immediate publication after certification. Provide a manual retry using the same release tag. Reject drafts, prereleases, foreign repositories, arbitrary download URLs and unmerged source. Preserve the CLI, Linux/Windows support, existing archive publication, private package identity and all non-package Store metadata.

This adds a Store update route alongside the existing full MSIX qualification route. It does not change the meaning of historical qualification records, claim all 19 acceptance gates passed on a fresh hosted runner, or automatically edit the Store listing. No new application dependency or Python runtime is introduced; Python and PowerShell remain CI/development tools.

## Trusted event and credential boundary

Use a credential-free `release: published` dispatcher for human/API releases and explicitly dispatch the same Store workflow after successful publication in `release.yml`. The latter is necessary because publication using `GITHUB_TOKEN` does not trigger another release-event workflow. Both dispatch `store-update.yml` at `main`, passing only a validated stable tag. The Store workflow accepts `workflow_dispatch` on `refs/heads/main` only. Its workflow and packaging/controller checkout use that run's exact `github.sha`, which must be committed on `main`; release source is resolved separately from the tag. No privileged job uses `pull_request_target`, a PR checkout, release-supplied executable scripts, or artifacts from an untrusted run. [GitHub event behavior](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

The protected `msix-packaging` environment is restricted to `main`. Reuse its four existing `CNMON_MSIX_*` secrets. Add `CNMON_STORE_TENANT_ID`, `CNMON_STORE_CLIENT_ID`, `CNMON_STORE_CLIENT_SECRET` and `CNMON_STORE_APP_ID` as environment secrets. The REST API needs no seller ID; do not add or disclose an unused one. Scope API secrets to the preflight and submission steps, so executable qualification processes do not inherit them. Never print access tokens, identity fields, API bodies, submission IDs, SAS upload URLs or raw HTTP errors. API responses, receipts, real packages and detailed reports remain job-local and are cleaned up. Public artifacts/summaries contain only allowlisted status tokens and public release/version/hash metadata. Do not use public Actions artifacts as private storage.

Serialize all Store operations using one repository-wide concurrency group with `cancel-in-progress: false`. PR tests use synthetic identities and mocked API responses, with no protected environment and no Store secrets. Pin third-party Actions to reviewed commit SHAs. Keep permissions at `contents: read` unless dispatch needs `actions: write`; publication and dispatch permissions belong only to the relevant trusted jobs.

## Release provenance and runtime metadata

Resolve a canonical stable tag `vMAJOR.MINOR.PATCH` through the owning repository's GitHub API. Require a published, non-draft, non-prerelease release. Resolve annotated tags to the exact commit and verify it is an ancestor of `main`. Require the exact Windows archive name `cn-mon_<version>_windows_amd64.zip`, the Linux archive and `SHA256SUMS`; reject duplicate/missing assets and malformed checksums. Hash downloaded assets and compare both the GitHub asset digest and the matching checksum entry. Allow only the owning repository's canonical GitHub asset URLs and validated GitHub asset download redirects. Bound download sizes and HTTP timeouts. Do not accept a URL input.

Pin release ID, tag commit, asset IDs and digests for the run, and re-read them immediately before the first Store mutation. Current `v0.3.0` reports `immutable: false`; these checks provide an explicitly pinned snapshot, not GitHub-enforced immutability. Reject replacement, deletion, tag movement or changed metadata rather than silently selecting new bytes. Future immutable releases are acceptable without depending on that setting.

Build a temporary release metadata file outside the checkout. Its existing packaging fields identify the selected archive name/root/hash, CLI version/revision, extracted executable hash and allocated Store package version; add public provenance fields needed by the controller. Validate the ZIP's four existing allowlisted files, safe paths, uniqueness and size before extraction. Native Windows must verify the executable's exact `--version` output. Never rebuild or patch the executable during packaging.

Add an explicit `-ReleaseMetadataPath` parameter to the existing packager and qualification entry points; default it to committed `packaging/windows/release.json` for existing callers. Validate the supplied metadata as one consistent contract. Replace the three fixed CLI `0.3.0` comparisons with comparisons to that contract; retain the existing archive, binary, manifest, receipt and installed-byte validation. Do not edit committed metadata at runtime or disable the clean-packaging-source check. This supports future published CLI versions while retaining the reproducible legacy package path.

Reuse `native.yml` through `workflow_call` with the exact release commit and owning repository before privileged packaging. This supplies native Linux and Windows runtime coverage; the package route additionally exercises the actual downloaded Windows executable. Existing release publication continues to own release archive qualification and delivery. A Store workflow is not permission to publish an unqualified CLI release.

## Package versions and duplicate handling

Store versions increase independently of CLI versions. Read every package version from the last published Store submission, validate each four-part version, and take the maximum together with the floor `1.3.2.0`. Allocate its next version by incrementing the third component, carrying into the second and first as needed; require components in `0..65535`, nonzero first component and zero fourth component. Fail on exhausted range. The first ordinary update above the current floor is `1.3.3.0`. Never derive Store version directly from CLI semver or GitHub run attempt.

Before allocating a version or mutating the Store, reject **any** pending submission. This deliberately includes a draft left by a previous interrupted automation run. Never delete, cancel, overwrite, resume or commit it automatically. An owner inspects that submission in Partner Center, resolves it, then retries. A repeated trigger therefore cannot destroy owner work or create a second pending update.

Append one machine-readable provenance marker to the cloned submission's private `notesForCertification` field, preserving the owner's note text and replacing only a previously recognized automation marker. The marker contains schema, release ID/tag/commit, archive SHA-256, packaging revision and package version. If the last published submission contains the same release/archive/packaging revision binding and its package matches that version, return `already_published` without mutation. Reject a release older than the latest recorded CLI release. If publication history lacks a marker, use the current pinned `0.3.0` baseline to reject older CLI releases. An exact GitHub rerun retains its packaging revision; a new manual dispatch after packaging source changes may deliberately create a newer package for the same CLI.

## Qualification policy

Keep the native qualification driver's full 19-gate contract and frozen completion-controller behavior unchanged. Introduce a separately named `StoreUpdate` aggregation profile in `msix-ci.ps1`. It requires these 17 gates to be `pass`: `identity`, `package_hash`, `signature`, `account`, `package_registration`, `exact_identity`, `installed_binary_hash`, `alias_identity`, `native_cli`, `icmp`, `history_config`, `shell_aliases`, `upgrade`, `uninstall_reinstall`, `fail_injection`, `cleanup` and `wack`. Hosted aggregation requires the same list except WACK (16 core gates); Certify aggregation requires all 17.

`conflicts` and `repair` must be present and may be `pass` or `incomplete`; either being `fail` rejects the update. These include visible Settings alias-toggle and Repair observations that fresh hosted runners cannot reliably provide; the automated `shell_aliases` gate remains required. Missing/unknown gates, malformed result objects, an overall hard failure or evidence-binding mismatch reject the update. WACK must run on this exact candidate and pass the existing strict parser, including DPI awareness. Preserve the actual 19-gate result, for example `17 passed, 0 failed, 2 incomplete`, alongside a separate `StoreUpdate: pass` decision. Never rewrite incomplete gates as pass or replay old package evidence for a new candidate.

Both the new Store route and the existing hosted CI wrappers explicitly use this automated aggregation policy. This is a documented CI policy change: a green hosted job means its automated gates passed, while its full qualification summary can remain incomplete. Keep `Assert-NativeResults` default full-policy behavior strict and pass the new policy explicitly from the Hosted/Certify wrappers. A worker exit code of 1 is acceptable only when the worker produced a valid, current evidence-bound report whose overall status is exactly `incomplete`, all required automated gates passed and only the permitted manual gates (plus pre-Certify WACK) are incomplete. Other exit codes, missing reports, hard failures or contradictory overall/gate states fail. Do not edit the pinned `.github/workflows/msix.yml` or frozen controller/evidence hashes merely to adopt this policy.

Reuse existing signing, installation, lifecycle, cleanup and WACK helpers. A disposable signed test copy remains separate from the unsigned MSIX uploaded to the Store; validate their recorded payload relationship. No production signing secret is needed. Continue to require a reviewed visible-desktop qualification update when package launch, alias or Repair behavior changes. Unchanged packaging contract and ordinary CLI updates do not require repeating screenshots and manual Settings operations for every release. The current Start-entry/display-name fixes have owner-reported successful submission, while historical full-desktop evidence retains its original package binding; do not represent that as a fresh 19/19 result for `1.3.2.0`.

## Store API transaction

Use the documented REST submission API with a small injectable HTTP adapter. Its explicit methods make pending-draft protection and byte-preserving metadata tests straightforward. Do not use a convenience publish operation that replaces a draft. The owner must first associate a Microsoft Entra application with Partner Center, assign the documented access, configure the four API secrets, and have a published baseline submission. [API prerequisites](https://learn.microsoft.com/en-us/windows/uwp/monetize/create-and-manage-submissions-using-windows-store-services)

The transaction is:

1. Obtain a short-lived client-credentials token. GET the app; require its identity to match all configured package identity fields returned by the API, a last published submission and no pending submission. GET the published submission and compute the version/duplicate decision. Preparation performs no Store writes.
2. After qualification, reacquire credentials, revalidate the release snapshot, app identity, absence of pending submission and unchanged published submission. Any intervening owner/API change stops the run.
3. POST a new submission; the API clones the last published submission. Validate the returned `id`, `status` and `fileUploadUrl` without printing them. Do not blindly retry this POST after an ambiguous network failure.
4. Preserve the cloned JSON deeply, including unknown fields, listing text, images, pricing, markets, age ratings, accessibility declarations and rollout settings. Change only `applicationPackages`, the defined provenance marker in `notesForCertification` and `targetPublishMode` to `Immediate`. Set replaced x64 package entries' `fileStatus` to `PendingDelete` and append the one new `.msix` with `fileStatus: PendingUpload`. Reject an unexpected package architecture or package shape rather than deleting it. Upload ZIP contains only this unsigned MSIX with the exact `fileName` referenced in JSON.
5. PUT the updated submission, upload the ZIP to the returned HTTPS Azure Blob SAS URL without a Store bearer token, then POST commit. Restrict API/token/upload hosts and reject redirects that could leak credentials. Never expose SAS parameters. Do not blindly repeat create/commit calls after a timeout.
6. Poll with bounded timeouts. `CommitFailed`, `PreProcessingFailed`, `CertificationFailed`, `ReleaseFailed`, `PublishFailed`, canceled or unknown status is failure. `PreProcessing`, `Certification`, `Release`, `Publishing` or `Published` confirms the commit was accepted; report `submitted` for intermediate states and `published` only for `Published`. A still-pending commit at the deadline is incomplete, not successful publication. Microsoft continues certification and automatic publication after the CI run ends. Future retries still honor the pending-submission guard.

Microsoft documents that creation copies the published submission and that commit begins ingestion; publication mode and package states are explicit fields. [Submission flow and resources](https://learn.microsoft.com/en-us/windows/uwp/monetize/manage-app-submissions) The app response exposes the published/pending references and package identity used for preflight. [App resource](https://learn.microsoft.com/en-us/windows/uwp/monetize/get-an-app)
